# Marathon 产品审计报告

日期：2026-06-03  
范围：主 Web App，包含首次进入、赛事库、档案填写、计划生成后指标、训练日历、桌面外壳。  
方法：Product Design audit。已抓取本地开发环境截图作为当前证据；同时阅读 `CONTEXT.md`、`PROJECT.md`、`PRODUCT_NOTES.md` 和核心组件代码。

## 截图证据

1. `01-mobile-first-races.png`：移动端首次进入，默认赛事页。
2. `02-mobile-profile-empty.png`：移动端档案页空状态。
3. `03-mobile-stats-after-generate.png`：填写 5km 成绩后生成计划，跳转指标页。
4. `04-mobile-calendar.png`：移动端训练日历。
5. `05-mobile-race-search-shanghai.png`：移动端赛事搜索“上海”。
6. `06-desktop-app-shell.png`：桌面宽屏访问。

## 一句话判断

这个产品已经不是“能不能用”的阶段，而是进入“要把主价值说清楚、把首轮体验打磨顺、把数据可信感做出来”的阶段。核心算法和训练日历有明显产品价值，赛事库也有潜力；但现在第一屏、信息架构和数据解释会让新用户不确定：这到底是赛事库，还是训练计划工具？

## 用户目标

最应该服务的主路径是：

1. 我有一个目标赛事，或者想找一个赛事。
2. 我输入自己现在的成绩。
3. 系统告诉我：我该怎么练、每周跑多少、今天跑什么。
4. 我能把计划带走：日历、手表、打卡、分享。

现在产品功能基本覆盖这条路径，但顺序和表达还没有完全对齐。

## 已经很强的地方

### 训练日历是当前产品的核心资产

截图 `04-mobile-calendar.png` 显示：今日训练、目标配速、心率区间、距比赛周数、打卡、月跑量、整月课表都在一个页面。这个页面有“我今天该干嘛”的直接价值，是产品最接近留存的地方。

### 算法可信度有基础

项目文档和代码里已经有 VDOT、COROS 区间、BMI 安全系数、目标差距、减量、恢复、休假覆盖、多赛事覆盖。这些不是普通日历工具能随便做出来的，是产品差异化。

### 赛事库有潜力成为获客入口

截图 `01-mobile-first-races.png` 和 `05-mobile-race-search-shanghai.png` 显示，赛事库已经有搜索、筛选、日期分组、我的赛事、手动添加。跑者天然会搜“上海马拉松/北京马拉松/厦门马拉松”，这是可被推广内容承接的入口。

### 移动端视觉方向成立

黑底、绿色强调、底部 Tab、底部 Sheet、分段按钮，整体接近手机 App，而不是传统网页。对跑者个人工具是合适的。

## 主要风险

### 1. 首屏定位偏了

证据：`01-mobile-first-races.png`。默认进入的是赛事页，而且当“报名中”为 0 时，用户第一眼看到的是大量未来赛事列表。  

问题：如果用户是被“小红书/朋友推荐”带来，他可能想要“生成训练计划”，但第一屏告诉他的却是“这是赛事列表”。这会削弱产品的一句话价值。

建议：首次进入应当是“从赛事到计划”的引导，而不是直接砸一个大赛事库。可以保留赛事页为入口，但顶部需要一个强引导卡：

> 选一场比赛，30 秒生成备赛计划  
> 已有目标？直接填成绩生成

更直接的做法：默认进入档案页，赛事页作为“选比赛”的辅助入口。

### 2. 生成计划后的下一步不够顺

证据：`03-mobile-stats-after-generate.png`。生成后跳到指标页。  

问题：指标页专业、可信，但用户最想看的通常是“我的课表长什么样”和“今天跑什么”。先给配速区间，可能像把说明书放在产品之前。

建议：生成后优先跳到训练页，并在训练页顶部展示一个“计划摘要”：

- 目标赛事：xxx
- 距比赛：xx 周
- 本周跑量：xx km
- 今天训练：xx
- 按钮：查看配速区间

指标页应该是“解释为什么这么练”，不是生成后的第一个落点。

### 3. 本地开发环境赛事数据回退暴露了产品可信风险

证据：`05-mobile-race-search-shanghai.png` 显示“本地种子数据 · 59 场”。  

问题：线上 Vercel 通过 `/api/data -> /races.json` 读完整数据，但本地 Vite 开发时 `/api` 代理到 crawler server，如果 crawler server 没跑，就回退到 seed。这对开发没问题，但产品层面需要处理“数据源失败时用户看到了什么”。

建议：

- 前端优先 fetch `/races.json`，失败再 fetch `/api/data` 或 seed，减少开发/线上差异。
- 赛事页底部不要只写“爬虫数据/本地种子数据”，要写成用户能理解的话：
  - 数据已更新至：2026-05-23
  - 来源：最酷、闹跑、CHINARUN、马拉松报名
  - 数据异常时：当前显示离线备用数据，可能不完整

### 4. 档案页表单很好用，但高级能力藏得太深

证据：`02-mobile-profile-empty.png`。核心输入清楚，CTA 很强；但高级设置被压在底部，且被 sticky CTA 和底部导航挤压。  

问题：对新手来说，这没问题；对认真跑者来说，LTHR、LT Pace、半马/全马 PB、目标时间是关键输入，被藏起来会降低“专业感”和计划精度。

建议：不要把所有高级项都折叠。可以改为两层：

- 必填：目标赛事、比赛日期、至少一个 PB
- 推荐填写：目标完赛时间、半马/全马 PB、身高体重
- 进阶：LTHR、LT Pace、长跑偏好日

这比“高级设置”更像教练在指导用户补资料。

### 5. 赛事库很强，但“报名中 = 0”时首屏情绪偏冷

证据：`01-mobile-first-races.png` 顶部显示报名中 0。  

问题：报名中为 0 是真实数据，但它会让用户觉得“没东西可做”。  

建议：当报名中为 0 时，不要把 0 做成主视觉。改成：

- 推荐关注的未来赛事
- 本月/下月热门赛事
- 你可能在找：上海、北京、厦门、成都、香港

也就是把“没有报名中”转译成“还能做什么”。

### 6. 训练日历信息密度偏高

证据：`04-mobile-calendar.png`。月历格子里同时有日期、距离、训练类型、描述、每周总量、当前日高亮。  

问题：功能很完整，但小屏可读性有风险。很多 9px、10px 的内容对普通用户和视力一般的人不友好。

建议：

- 月历格子只保留：日期、颜色、类型短标签、距离。
- 详细描述放到底部 Sheet。
- 周跑量可以放在每周行右侧，但不要和训练文字抢空间。
- 提供“列表视图/本周视图”，作为更适合手机的主视图。

### 7. 桌面端只是放大版手机 App

证据：`06-desktop-app-shell.png`。宽屏上中间只有一个窄列，周围大量黑色空白。  

问题：如果产品主要在手机使用，这可以接受；但如果用户从电脑打开、从 GitHub/Vercel/朋友链接打开，桌面首印象会显得“还没为桌面准备好”。

建议：桌面端不需要完整重做，但至少加一个两栏结构：

- 左侧：当前 Tab 主内容
- 右侧：计划摘要、我的赛事、今日训练、数据更新时间

### 8. 可访问性风险集中在小字、低对比和图标按钮

证据：多张截图中存在大量 `10px/11px` 字、低透明灰字、只有图标或短标签的按钮。  

风险：

- 灰字在黑底上视觉层级优雅，但部分对比度可能偏低。
- 底部导航禁用态透明度很低，可能被误解为不可见。
- 日历格子和赛事筛选 chip 的触控目标在视觉上偏小。
- 关闭按钮、删除按钮、图标按钮需要确认 aria-label。

建议：

- 关键说明最小字号提高到 12px。
- 非装饰图标按钮补 `aria-label`。
- 筛选 chip 和日历点击区保证 44px 左右触控目标。
- 不要依赖颜色单独表达状态，搭配文字或形状。

### 9. Intervals.icu 同步需要更强安全解释

证据：代码中 API Key 和 Athlete ID 存在 Zustand persist，也就是 localStorage。  

问题：这是合理的纯前端方案，但用户需要知道“凭据只保存在本机浏览器”。否则同步 API Key 会让人犹豫。

建议：在输入 API Key 的 sheet 里加一句：

> API Key 只保存在你的浏览器本地，不上传到我们的服务器。

同时提供“清除连接”按钮。

### 10. 产品还缺一个可传播的结果页

目前用户生成计划后，最容易分享的是截图，但产品没有主动给“分享成果”。  

建议做一个“计划卡片”：

- 我的目标：2026 上海马拉松
- 备赛周期：17 周
- 本周跑量：xx km
- 目标配速：x'xx"
- 今日训练：xx
- 底部小字：用马拉松备赛生成

这对小红书、跑群、朋友推荐都很重要。

## 机会区

### 最佳产品定位

不要只说“马拉松训练计划生成器”。更强的定位是：

> 从选赛到每天训练的马拉松备赛助手。

理由：你同时有赛事库、计划生成、日历、打卡、导出。单独说训练计划，浪费了赛事库；单独说赛事库，又浪费了算法。

### 最强增长入口

赛事库适合拉新，训练日历适合留存，分享卡适合传播。

建议主增长闭环：

1. 小红书/BBS 内容引导用户搜赛事。
2. 用户在赛事页找到目标比赛。
3. 一键生成备赛计划。
4. 用户看到今日训练和计划卡。
5. 用户分享计划卡或打卡卡。

### 最该保留的克制

现在不要急着做账号、社区、AI 聊天。  
当前产品最该做的是把无账号、本地存储、无需订阅这套轻量体验打磨到非常顺。

## 我对下一版的要求

### 必须做

1. 重新设计首次进入体验：明确告诉用户“选比赛/填成绩/生成计划”。
2. 生成计划后默认跳训练页，而不是指标页。
3. 赛事数据状态用户化：更新时间、来源、失败回退说明。
4. 修复本地开发时 `/api/data` 回退到 59 条 seed 的体验差异，至少前端优先读 `/races.json`。
5. 训练页做一个“本周/今日优先”的手机视图，降低月历密度。

### 应该做

1. 计划摘要卡：生成后马上给用户一个“这就是你的计划”的确认感。
2. 分享卡：目标赛事 + 周期 + 今日训练 + 配速区间。
3. 档案页把“推荐填写”从“高级设置”里拿出来。
4. Intervals.icu 增加本地保存说明和清除凭据入口。
5. 桌面端加右侧摘要栏。

### 可以晚点做

1. 账号云同步。
2. 社区功能。
3. AI 自然语言教练。
4. 更复杂的赛事数据标牌、高程、天气。

## 推荐版本规划

### V1.1：首轮体验修正

目标：让新用户 1 分钟内理解并生成计划。

- 默认首屏改成“生成计划”导向，赛事作为辅助入口。
- 生成后跳训练页。
- 增加计划摘要卡。
- 优化 sticky CTA 和底部导航的间距。

### V1.2：赛事库可信度

目标：让用户相信赛事库是真数据、可追溯、可更新。

- 显示数据更新时间和来源。
- 显示多源确认。
- 处理数据失败回退文案。
- 赛事详情里解释“报名中/即将开赛/日期待定”的含义。

### V1.3：训练留存

目标：让用户每天回来打卡。

- 本周视图。
- 今日训练更强。
- 打卡后生成分享卡。
- 日志页增加“过去 7 天表现”和下周建议。

## 证据限制

- 本次截图来自本地开发环境，不是线上 Vercel 页面。
- 本地 `/api/data` 未连接 crawler server，所以赛事页截图显示 seed 数据 59 条；线上通常会通过 `/races.json` 读取完整数据。
- 截图审计不能证明完整键盘可访问性、屏幕阅读器体验、真实外链报名成功率、手表导入成功率。

## 总结

产品核心是成立的，而且训练日历已经有“可留存”的感觉。现在最大问题不是功能不够，而是主路径的叙事顺序不够好：赛事库、档案、指标、训练四块都强，但用户第一次进来时不知道该先信哪个、做哪个、看哪个。

下一步不要大改算法，也不要急着做社区。先把“从选赛到今日训练”的第一轮体验磨顺，这个产品就会从“功能完整”变成“别人愿意推荐”。
